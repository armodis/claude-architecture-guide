CLAUDE.md substrate

One system behind a fleet of Claude sessions

Layered CLAUDE.md instructions, skills, agents, and settings — scoped by domain and coordinated through GitHub — so every Claude session behaves consistently and works in concert, wherever it runs. Four concerns, one shared component. It's all public Claude Code features: clone the template repo, edit one config block, and run setup.sh to stand up your own.

source of truth: one git repo deploy: stow + symlinks wiring: setup.sh built on: public Claude Code features

Concern 01

Separation of concerns

Instructions are scoped by directory depth. Claude Code walks from ~/ down to the working directory and stacks every CLAUDE.md it passes — each layer inherits everything above and adds its own.

The three-layer cascade

Shown for a session launched in ~/work/app/. The load-order scopes are a documented feature — user, then project, then nested subdirectory.

Layer 0 · User / global — every session

~/.claude/CLAUDE.md

Working habits, output style, markdown rules, machine System Notes.

Layer 1 · Domain root — the whole tree

~/work/CLAUDE.md

Domain conventions: repo directory, launch rules, cross-repo assumptions.

symlink ← claude-domains/work/CLAUDE.md

inherits ▾
Layer 2 · Project / repo — when launched here

~/work/app/CLAUDE.md

Repo context: pipeline, board, multi-agent workflow. Committed in the repo, not in dotfiles. Nests further (app/backend/, app/ui/).

lives in the work/app repo clone

Two domains, one firewall

Both hang off the shared global layer, but neither inherits the other. The split is declared: personal/CLAUDE.md states it applies to ~/personal/* and not ~/work/.

Work

~/work/

Day-job work. Each sub-dir is a separate repository clone with its own CLAUDE.md.

  • app/main application
  • infra/infrastructure
  • …your other work repos
no inheritance

Personal

~/personal/

Personal / family. Less-formal tone; extra care on legal, finance, health.

  • dotfiles/this substrate
  • home/household
  • …your other personal repos
Set it up: the whole cascade is the documented CLAUDE.md load order plus path-scoped rules — no custom tooling required.

Concern 02

Agent-team orchestration

Several Claude sessions may touch the same repo at once. Coordination doesn't live in any session — it lives in GitHub, so the state survives whichever surface or machine shows up next.

Shared state plane. Issues are the task queue, the project board Status is the lock, STATUS.md is the narrative, and git worktrees keep parallel impl work isolated. Any session reads the same truth.  

The roster — .claude/agents/

Named subagents composed into review/audit teams (Claude Code's built-in agent-teams feature). Team specs live in .claude/teams/; the review checklists and pipeline steps are skills under .claude/skills/ (custom slash commands are the same mechanism).

What every agent must do

STATUS.md
Read it first on entering a repo; update it before leaving.
Claim first
Flip board Status ToDo → In Progress (the queryable lock), log it in STATUS.md with session + date, commit to main with a status: prefix.
Select work
Open labeled ToDo, sorted Priority ASC, Effort ASC, Created ASC, head first. Skip (warn) any missing Priority/Effort. Modes: quick-wins · focused-feature · backlog-cleanup.
Worktrees
Impl runs in a git worktree on a feature branch. status: → main directly; impl: → the branch, landing via PR. Re-base every path onto the worktree root.
Commits
analysis:plan:impl:status:feat:fix:docs:chore:
Decisions
For a reversible call that would block on a human, run a Green Doc (direction) → Blue Doc (execution) review and proceed, recording the outcome.
Escalate
Always hand to a human for irreversible / outward-facing actions — deleting non-recreatable data, force-push, external comms, editing others' issues.

These are project conventions written into the repo's own CLAUDE.md — the mechanism is public; the policy is yours to define.

Concern 03

Configuration portability

One repo is the source of truth; a single script rebuilds the whole environment on any machine. Nothing that drives Claude is hand-placed — it's all symlinks back into version control.

How it deploys

setup.sh uses GNU Stow for whole-directory package installs and per-file symlinks where two sources share a target. Real files found in the way are backed up first.

  • claude-user/stow → ~/.claude/ — CLAUDE.md, settings.json, statusline
  • claude-domains/symlink → ~/work/ & ~/personal/ domain roots
  • bash/ · git/stow → ~/ — shell + git config

What travels in settings.json

Model, effort level, enabled plugins, permission allowlist, statusline command, theme — the whole operating profile moves with the repo. Every key is documented in the settings reference.

Cross-OS, not just this laptop. The permission allowlist carries Windows entries (powershell:*, copy:*, /c/Users/…) alongside the Linux ones — the same repo deploys on Linux and Windows.
# clone the template, edit the config block, deploy
git clone https://github.com/armodis/claude-architecture-guide
cd claude-architecture-guide
$EDITOR setup.sh   # set DOMAINS=(work personal ...)
./setup.sh         # stow + symlink (backs up real files first)
./verify.sh        # confirm the wiring

The repo ships a template/ scaffold (universal Layer 0 + example work/personal domain roots + shell/git dotfiles). Copy it into your own dotfiles repo, or run in place.

Concern 04

Agent surfaces

The same instructions drive Claude wherever it runs. Per the Claude Code docs: “each surface connects to the same underlying engine, so your CLAUDE.md files, settings, and MCP servers work across all of them.”

Two config planes

User-local
~/.claude/ ← dotfiles
Deployed by stow onto machines you set up. Reaches local surfaces — the CLI and Desktop — but not a cloud clone.
Repo-committed
<repo>/.claude/ + CLAUDE.md
Committed in each repo, so it travels with the clone to any surface — including web / cloud Claude Code — via standard project resolution.

Where it runs

Claude Code CLI
Local TUI, fullscreen. Both planes.
local + repo
Claude Desktop
Local app on the same machine.
local + repo
Web Claude Code
Cloud clone; sees committed repo config only.
repo plane
Chat / Mobile
Reads/writes the same GitHub state; push notifications on.
shared state
Why it composes. Because task state lives in GitHub — issues, board Status, STATUS.md, worktrees — plus any MCP servers you connect, a web session, the desktop app, and a laptop CLI collaborate on the same work without sharing local state. The substrate makes each surface consistent; externalized state makes them coordinated.

Component ◆

Portfolio Mgmt

The shared state plane, made concrete. A single GitHub Projects board tracks work across all your repos — app · infra · automation · planning · site. It's the task graph agents claim from, audit, and sync against.

Copy a ready-made board. Both boards below are GitHub Projects templates — open one and hit Copy to start pre-wired with the fields and lifecycle in this panel:
◆ Strategic Portfolio → ◆ Personal Task Mgmt →
No org of your own? Build it from the fields below by hand.

Status lifecycle

ToDo→ Backlog→ In Progress→ Pending Release→ Done

In Progress doubles as the queryable claim lock that stops two sessions grabbing the same issue. Pending Release is optional — use it for a repo where merged ≠ shipped; others go merged → Done.

Work hierarchy — Category × Type

Every item carries a Category (planning level) and Type (work kind). Themes are pillars with no issue of their own.

Fields agents read most

Plus Effort, Iteration, Rank, WBS, Quarter, Business Value… (all standard GitHub Projects custom fields). Iteration IDs are dynamic — always discover them live, never hardcode.

What keeps it in sync

Automatic

GitHub Actions — the happy path; status/theme/type rollups on issue & PR events.

On-demand

/project-sync — audits board vs. real GitHub state, proposes corrections.

On-demand

/audit-fields — field-accuracy detector; auto-applies high-confidence fixes, surfaces the rest.

Human

Manual — PMs set initial Priority/Theme, assign iterations, disposition findings.

Read https://github.com/armodis/claude-architecture-guide end to end, then inspect my current setup (~/.claude, dotfiles, git config, GitHub account).
